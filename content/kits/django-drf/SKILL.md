# Django + DRF

This is how we build a Django service: Django 5.2 LTS, DRF, Celery on Redis, Postgres 16, Python 3.13 with uv,
deployed as one container image to DigitalOcean App Platform. Copy the templates; they are real, tested files.

## Layout

```
config/                 project package: settings/, urls.py, wsgi.py, asgi.py, celery.py, gunicorn.py
apps/core/              shared plumbing: request ids, logging, error envelope, pagination, health
apps/<domain>/          one app per domain (billing, contracts, ...), each with its own tests/
conftest.py             fixtures shared by every app's tests
manage.py, pyproject.toml, uv.lock, Makefile, Dockerfile, compose.yml, .do/app.yaml
```

- Organise by domain, not by layer: an app holds its models, serializers, views, tasks, admin and `tests/`.
  Business rules live in models and service functions inside the app, never in serializers or views.
- Start every project with a custom user model in `apps/accounts` (`AUTH_USER_MODEL = "accounts.User"`)
  before the first migration, because swapping it later means rewriting history.
- The API lives under `/api/v1/`. Each app's ViewSets are registered on the one `DefaultRouter` in
  `config/urls.py`. `/healthz`, `/readyz` and `/admin/` sit outside the versioned prefix.
- Authentication is JWT (simplejwt): `/api/v1/auth/token/`, `.../refresh/` (rotating, old refresh tokens
  blacklisted) and `.../blacklist/` for logout. The default permission is `IsAuthenticated`; a public
  endpoint opts out explicitly with `permission_classes = (AllowAny,)` and a throttle.
- The OpenAPI schema is generated by drf-spectacular at `/api/v1/schema/` (UI at `/api/v1/docs/`), served to
  staff signed in to the admin. A test fails the build when the schema generates with warnings.

Where the product is multi-tenant, every tenant-owned row carries `tenant_id` and every ViewSet over such a
model scopes at the queryset, so no endpoint can read or write across tenants:

```python
class TenantScopedQuerysetMixin[M: Model](GenericAPIView[M]):
    """Every read and write of a tenant-owned model stays inside the caller's tenant."""

    def get_queryset(self) -> QuerySet[M]:
        return super().get_queryset().filter(tenant_id=self.tenant_id)

    def perform_create(self, serializer: BaseSerializer[M]) -> None:
        serializer.save(tenant_id=self.tenant_id)

    @property
    def tenant_id(self) -> UUID:
        user = self.request.user
        # IsAuthenticated has already rejected anonymous callers.
        if not isinstance(user, User):
            raise TypeError("tenant-scoped views need an authenticated user")
        return user.tenant_id


class InvoiceViewSet(TenantScopedQuerysetMixin[Invoice], viewsets.ModelViewSet[Invoice]): ...
```

Another tenant's row is a 404, never a 403. Each tenant-scoped app tests that a second tenant's rows are
neither listed, retrieved, updated nor deleted.

## Settings

- `config/settings/{base,local,test,production}.py`, selected with `DJANGO_SETTINGS_MODULE=config.settings.<env>`.
  `base` holds everything shared; the others import it and override. Add `staging` only where the project has one.
- Values come from the process environment through django-environ (compose `env_file`, CI, App Platform).
  Nothing reads a `.env` file at runtime. `.env.example` lists every variable with a placeholder.
- `production` hard-codes `DEBUG = False`, trusts `X-Forwarded-Proto` (`SECURE_PROXY_SSL_HEADER`, App Platform
  terminates TLS), redirects to HTTPS, sends HSTS for a year and marks session and CSRF cookies secure.
  `DJANGO_SECRET_KEY`, `DJANGO_ALLOWED_HOSTS`, `DJANGO_CSRF_TRUSTED_ORIGINS`, `DATABASE_URL` and `REDIS_URL` have
  no defaults: a missing one stops the process at start-up, which the settings tests prove.
- `test` needs only `DATABASE_URL`; Celery runs tasks inline there.
- i18n is on: `LANGUAGE_CODE = "es"`, `LANGUAGES` es and en, `LocaleMiddleware`, `LOCALE_PATHS = [BASE_DIR / "locale"]`.
  API error messages follow the caller's `Accept-Language`.
- Postgres 16 everywhere, including tests, because SQLite hides constraint, JSON and locking differences.
  Deviate when the project context says so, e.g. telemetry projects run TimescaleDB (`timescale/timescaledb:2.x-pg16`).
- Migrations follow the `migrations` default rule. Here that means: every migration is backwards-compatible with
  the running code and ships in a deploy before the code that needs it; `make check` fails on a model change
  without a migration (`makemigrations --check --dry-run`); the App Platform `PRE_DEPLOY` job applies them.

## Logging

- structlog renders every line, from our code, Django, Celery and gunicorn alike, as one JSON object on stdout
  (`apps/core/logging.py`). Log events as snake_case names with fields: `logger.info("invoice_sent", invoice_id=id)`.
- `RequestIdMiddleware` binds `request_id` from the incoming `X-Request-ID` (when short and log-safe) or a new
  uuid4 hex, echoes it in the response header and logs one `request_finished` line per request. Successful
  `/healthz` and `/readyz` probes log at DEBUG only.
- In Celery, `task_id` and `task_name` are bound for the task's duration, and the `request_id` of the request
  that queued the task travels in the task headers (`apps/core/celery_signals.py`).
- Redaction runs on every line: keys containing `password`, `secret`, `token`, `authorization`, `cookie`,
  `session`, `api_key`, and personal data keys (`email`, `phone`, `address`, `iban`, `dni`, `nie`, `nif`), at any
  depth. Tracebacks are structured and never include frame locals. Add keys to the lists, never remove them.
- Never swallow an exception: log it with context and re-raise, or handle it and say why in the log.

## Errors

Every non-2xx API response, including validation, 401, 403, 404, 405, 429 and 500, has one shape:

```json
{"error": {"code": "snake_case_code", "message": "Human readable sentence.", "details": null, "request_id": "..."}}
```

- `apps/core/exceptions.py` is DRF's `EXCEPTION_HANDLER`. Validation errors use code `validation_error` with
  `details` as `{"field": ["message", ...]}` (`non_field_errors` for the rest); Django's `ValidationError`,
  `PermissionDenied` and `Http404` are translated the same way.
- Unexpected exceptions log at ERROR with the stack trace and answer `internal_error` with a generic message;
  exception text never reaches the client. `handler404` and `handler500` give `/api/` paths the same envelope.
- Raise DRF exceptions (or `ValidationError` from a serializer) with a specific `code`; clients branch on `code`,
  never on `message`.
- Every list endpoint is paginated by `StandardPagination`: `page` and `page_size` (default 50, max 200), response
  `{"count", "next", "previous", "results"}`. A page past the end is a `not_found` error.

## Tests

- pytest with pytest-django, against Postgres. Each app keeps its tests in `apps/<domain>/tests/test_*.py`;
  shared fixtures (`api_client`, `user`, `auth_client`) live in the root `conftest.py`.
- Test through the API with `APIClient` for endpoints, and call service functions directly for business rules.
  Name tests for the behaviour: `test_another_tenants_row_is_not_found`.
- Warnings are errors (`filterwarnings = ["error"]`), so deprecations surface in the PR that causes them.
- Mark tests that take over a second with `@pytest.mark.slow`; `make check-fast` skips them.
- Coverage is a floor of 80% (branch coverage), enforced in `make check`.
- `apps/core/tests/` covers the shipped plumbing: request ids, logging and redaction, Celery context, error
  envelope, pagination, health, auth and production settings. Keep it green when you change the plumbing.

## Makefile targets

Tooling runs in the container: `docker compose run --rm app make check`. CI runs the same `make check`.

| Target | What it runs |
|---|---|
| `make check` | ruff lint, ruff format check, mypy (strict, django-stubs + djangorestframework-stubs), pytest with coverage floor, `makemigrations --check --dry-run`, pip-audit on the locked production dependencies |
| `make check-fast` | lint, format check, mypy, `pytest -m "not slow" -x`; narrow it with `make check-fast TESTS=apps/billing` |
| `make install` | `uv sync --locked` |
| `make format` | `ruff format` and `ruff check --fix` |
| `make test`, `make run`, `make worker`, `make migrate` | pytest, dev server, Celery worker, migrations |

The gate targets always use `config.settings.test`. Kits and projects add prerequisites through `make/*.mk`
fragments, included at the end of the Makefile.

## Container

- One multi-stage `Dockerfile`. The builder stage installs locked production dependencies with uv into
  `/app/.venv` (dependency layer before source), compiles translations when the project has `.po` files and
  collects static files. The runtime stage is `python:3.13-slim-bookworm` pinned by tag and digest, runs as uid
  10001, serves with gunicorn (`config/gunicorn.py`, JSON logs) and static files with WhiteNoise.
- The `dev` stage adds dev dependencies, make and gettext; compose builds it and mounts the source.
- `HEALTHCHECK` calls `/healthz` with the Python standard library. `HealthCheckMiddleware` answers `/healthz` and
  `/readyz` before host validation and the HTTPS redirect, because probes arrive over plain HTTP with an
  internal Host header.
- `/healthz` is liveness and touches nothing. `/readyz` checks the database and answers 503 with
  `{"status": "unavailable", "checks": {...}}` when it cannot reach it.
- `compose.yml` runs app (dev server), worker, Postgres 16 and Redis 7 with health-gated start-up, for local work
  only. Deviate when the project context says so, e.g. octosentinel uses RabbitMQ as the Celery broker.

## Deploy path

1. A PR runs `ci`: `check` (`make check` against a Postgres service), `secrets` (gitleaks CLI over the full
   history) and `image` (build plus a `/healthz` smoke test). Every action is pinned to a commit SHA.
2. A green `ci` run on a push to `main` triggers `deploy`, in the GitHub `production` environment. A run that is
   no longer the tip of `main` stops with a notice; the newer run deploys.
3. `digitalocean/app_action` applies `.do/app.yaml`: web service on port 8000 with health check `/healthz`, a
   Celery worker from the same image (`celery -A config worker`), a `PRE_DEPLOY` job running
   `python manage.py migrate --noinput`, and the managed Postgres 16 cluster bound as `DATABASE_URL`.
4. Secrets (`DJANGO_SECRET_KEY`, `REDIS_URL`) live in the GitHub `production` environment; `deploy.yml` passes
   them to the action, which substitutes them into the spec as `type: SECRET` values. Nothing secret is committed.
   The action turns an unset `${NAME}` into an empty string, which would wipe the stored secret, so a guard step
   fails the deploy when any variable the spec references is missing from the job env.
